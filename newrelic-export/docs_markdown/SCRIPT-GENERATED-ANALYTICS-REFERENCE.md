# Script-Generated Analytics Reference

Reference for the usage analytics files generated under `account_ACCOUNTID/_usage_analytics/` when the `--usage` flag is passed.

These files are generated by running NRQL queries against your New Relic account's audit and consumption data. They provide migration intelligence not available from configuration exports alone.

---

## Overview

| File | Purpose | Data Source | Time Range |
|---|---|---|---|
| `dashboard_views_top100.json` | Prioritize dashboards for migration | `NrAuditEvent` | 90 days |
| `alerts_most_fired.json` | Identify high-value alert conditions | `NrAiIncident` | 90 days |
| `users_most_active.json` | Discover stakeholders and active users | `NrAuditEvent` | 90 days |
| `ingest_by_data_type.json` | Plan data migration and capacity | `NrConsumption` | 30 days |

---

## dashboard_views_top100.json

Top 100 dashboards ranked by view count over the last 90 days.

**Use for:** Prioritizing which dashboards to migrate first. High-view dashboards have the most business impact and should be migrated before low-traffic ones.

**NRQL Query:**
```sql
SELECT count(*) AS 'views', latest(timestamp) AS 'lastViewed'
FROM NrAuditEvent
WHERE actionIdentifier = 'dashboard.view'
FACET targetId
LIMIT MAX
SINCE 90 days ago
```

**Schema:**
```json
[
  {
    "targetId": "MTIzNDU2N3xWSVp8REFTSEJPQVJE...",
    "views": 1847,
    "lastViewed": 1745232000000
  }
]
```

**Migration guidance:**
- Cross-reference `targetId` with `dashboards/dashboards.json` → `guid` to identify dashboard names
- Dashboards with 0 views in 90 days are elimination candidates
- High-view dashboards should be validated in Dynatrace before cutover

## alerts_most_fired.json

Alert conditions ranked by incident count over the last 90 days.

**Use for:** Identifying which alert conditions are actively firing and must be migrated with high fidelity. Conditions that have never fired are elimination candidates.

**NRQL Query:**
```sql
SELECT count(*) AS 'fired'
FROM NrAiIncident
FACET conditionName
LIMIT MAX
SINCE 90 days ago
```

**Schema:**
```json
[
  {
    "conditionName": "High Error Rate - checkout-service",
    "fired": 23
  }
]
```

**Migration guidance:**
- Conditions with 0 fires over 90 days: review with stakeholders before migrating
- High-fire conditions: validate equivalent DQL thresholds carefully
- Cross-reference with `alerts/nrql_conditions.json` → `name`

## users_most_active.json

Top 50 users ranked by audit event count over the last 90 days.

**Use for:** Identifying key stakeholders to involve in migration validation. The most active users are most likely to notice regressions.

**NRQL Query:**
```sql
SELECT count(*) AS 'actions'
FROM NrAuditEvent
FACET actorEmail
LIMIT MAX
SINCE 90 days ago
```

**Schema:**
```json
[
  {
    "actorEmail": "jane.smith@example.com",
    "actions": 3421
  }
]
```

**Migration guidance:**
- Top 10 users: prioritize for UAT and migration sign-off
- Users with 0 activity in 90 days may not need accounts in Dynatrace
- Cross-reference with `_rbac/users.json` (if exported with `--rbac`)

## ingest_by_data_type.json

Data ingestion volume broken down by New Relic data type (Events, Metrics, Logs, Traces) over the last 30 days.

**Use for:** Planning data migration scope and Dynatrace ingest capacity. Identifies which data types to prioritize for pipeline setup.

**NRQL Query:**
```sql
SELECT bytecountestimate() / 1e9 AS 'daily_gb'
FROM NrConsumption
WHERE usageMetric = 'EventsBytes'
FACET metric
SINCE 30 days ago
LIMIT MAX
```

**Schema:**
```json
[
  {
    "metric": "LogBytes",
    "daily_gb": 145.3
  },
  {
    "metric": "MetricsBytes",
    "daily_gb": 67.8
  },
  {
    "metric": "TracingBytes",
    "daily_gb": 23.1
  }
]
```

**Migration guidance:**
- High log volume → plan Dynatrace Log Management capacity and OpenPipeline rules
- High metrics volume → plan Dynatrace Metrics ingest and metric key mapping
- High trace volume → validate Dynatrace Distributed Tracing sampling rates
- Use 30-day total to size Dynatrace DDU/ingest entitlements

## Using Analytics for Migration Prioritization

### Priority Matrix

```
HIGH VIEWS + HIGH FIRES   → Migrate first (maximum business impact)
HIGH VIEWS + NO FIRES     → Migrate early (used dashboards, quiet alerts — review thresholds)
NO VIEWS + HIGH FIRES     → Investigate (automated alert, no human review — may be redundant)
NO VIEWS + NO FIRES       → Eliminate or defer (no demonstrated value in 90 days)
```

### Recommended Migration Order

1. Export usage analytics with `--usage`
2. Cross-reference `dashboard_views_top100.json` with `dashboards.json` to build ranked list
3. Cross-reference `alerts_most_fired.json` with `nrql_conditions.json` to identify active conditions
4. Identify top 10 users from `users_most_active.json` as migration stakeholders
5. Review `ingest_by_data_type.json` to scope OpenPipeline and ingest configuration

## Data Availability Notes

| Metric | Availability |
|---|---|
| `NrAuditEvent` retention | Typically 30–90 days depending on account tier |
| `NrAiIncident` retention | 13 months |
| `NrConsumption` | Available on accounts with Data Plus or usage-based pricing |
| Dashboard view tracking | Requires `NrAuditEvent` access; may be restricted on some account tiers |
