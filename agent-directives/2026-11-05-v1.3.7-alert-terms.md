## 2. What the change is, and why

**Bug:** the exporter's `nrqlConditionsSearch` NerdGraph query selected only `id name description enabled entityGuid policyId nrql{query} expiration{…}`. It never selected `terms`, so **every exported NRQL alert condition had no threshold**. Downstream, the converter fell back to threshold `0`, a 60 s duration and CRITICAL priority. It also never saw `signal.aggregationWindow`, so every condition was routed to a Davis anomaly detector and none to an alert pool. `EXPORT-SCHEMA.md` already documented all of these fields; the script just never selected them.

**Fix (bash v1.3.7, PowerShell v1.0.3):** the conditions query also selects:

```graphql
type runbookUrl violationTimeLimitSeconds
terms { threshold thresholdDuration thresholdOccurrences operator priority }
signal {
  aggregationWindow aggregationMethod aggregationDelay aggregationTimer
  fillOption fillValue slideBy evaluationDelay
}
... on AlertsNrqlBaselineCondition { baselineDirection }
... on AlertsNrqlOutlierCondition { expectedGroups openViolationOnGroupOverlap }
```

**Verified against NerdGraph on 2026-11-05:**
- The top-level `terms` selection is accepted for every condition type, so no per-type fragments are needed for it. Both fragments parse.
- Test account: 47 conditions (42 STATIC, 5 BASELINE). 47/47 now export `terms`, with 0 null thresholds; 47/47 export `signal.aggregationWindow`; 5/5 baselines export `baselineDirection`.
- A BASELINE condition's `terms[].threshold` is a number of **standard deviations**, not a value of the query result. It is still numeric (3.0 and 4.0 here).

**Second fix, PowerShell only:** six `Log-Debug` strings wrote `"$page:"` / `"$batchNum:"`. PowerShell reads `$name:` as a scope-qualified variable, so **the whole `.ps1` failed with a ParserError and never ran**. The fix is `${page}:` / `${batchNum}:`. Check whether R1's `.ps1` has the same lines.

**Known issue, NOT fixed here:** the `.ps1` service-level export queries `actor.account.serviceLevel.indicators`, which NerdGraph rejects ("Cannot query field serviceLevel on type Account"). The bash script moved to an entity-based query in its v1.3.3. On Windows, `-All` / `-ServiceLevels` therefore throw (`The property 'Count' cannot be found`) and write no archive. Runs with `-Dashboards -Alerts -Synthetics -Workloads` complete. Record it as a known issue; porting it is out of scope.

**Measured effect** (converter `@dma/newrelic-converter` parsing both archives):

| | Old archive (v1.3.6) | New archive (v1.3.7) |
|---|---|---|
| Conditions with terms | 0 / 47 | 47 / 47 |

| Distinct thresholds | 1 | 24 |

## 3. Optional end-to-end check (needs a built `@dma/newrelic-converter` and two archives)

```js
// node e2e.cjs <converter>/dist/index.js <old-archive.tar.gz> <new-archive.tar.gz>
const { ArchiveParser, AlertConverter, resolveDefaultApproach } = require(process.argv[2]);
(async () => {
  for (const [label, file] of [["old", process.argv[3]], ["new", process.argv[4]]]) {
    const parsed = await new ArchiveParser().parse(file);
    const conds = parsed.alertPolicies.flatMap(p => p.conditions);
    const out = new AlertConverter().convertMany(parsed.alertPolicies);
    const events = out.results.flatMap(r => r.output?.metricEvents ?? []);
    const approach = {};
    for (const c of conds) { const a = resolveDefaultApproach(c); approach[a] = (approach[a] || 0) + 1; }
    console.log(label, JSON.stringify({
      conditions: conds.length, withTerms: conds.filter(c => c.terms?.length).length,
      metricEvents: events.length, thresholdZero: events.filter(e => e.threshold === 0).length,
      distinctThresholds: new Set(events.map(e => e.threshold)).size,
      types: [...new Set(conds.map(c => c.type))], approach,
    }));
  }
})();
```

Expect `withTerms` to jump from 0 to all conditions, and `thresholdZero` to drop to only the genuinely "above 0" conditions. Confirm each by name.
